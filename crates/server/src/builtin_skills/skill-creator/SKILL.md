# Denia 技能创建器

帮助用户创建或维护 Denia 技能。技能是按需加载的工作流说明，不是泛化的系统提示，也不会自动授予额外文件或命令权限。

## 技能目录

优先按用户指定的位置写入；未指定时使用当前项目的 `.denia/skills/<skill-name>/`。需要跨项目复用时使用 Denia 数据目录的 `skills/<skill-name>/`。项目技能优先于用户技能，同名项目技能会覆盖用户技能。

每个技能目录必须有 `SKILL.md`：

```text
skill-name/
├── SKILL.md                 必需：入口说明
├── references/              可选：只在特定模式需要的详细资料
├── scripts/                 可选：可重复执行且值得自动化的脚本
└── assets/                  可选：模板、图片或生成结果所需资源
```

不要为了形式创建 README、变更日志或空目录。只有实际工作流会读取的资源才应加入技能。

## SKILL.md 格式

文件必须以 YAML frontmatter 开始，至少包含 `name` 和 `description`：

```yaml
---
name: example-skill
description: 在需要处理某类任务时提供具体工作流和判断标准。
---
```

名称只能使用小写字母、数字和连字符，且应保持简短。描述用于技能发现，应说明技能解决什么问题以及何时使用；不要把所有细节塞进描述。

正文应包含：

- 预期结果和适用范围；
- 会改变决策的领域约束；
- 需要时才读取的 references 路由；
- 脚本或资源的使用方式；
- 明确的边界、失败条件和验证方式。

假设 Denia 已经具备通用推理、文件和命令能力，只写该技能新增的知识。不要重复 Denia 的通用权限规则，也不要凭一个示例扩张成无条件要求。

## 渐进式加载

技能目录和描述会先被发现，`SKILL.md` 正文只在技能被调用时加载。把共享入口和选择标准放在 `SKILL.md`，把大型规范、格式说明或供应商细节放到 `references/`，并在入口中说明何时读取它们。

资源路径必须相对于技能的 `resourceBase`。需要读取资源时使用 Denia 的 `skill` 工具：先 `action=load`，再用 `action=resource` 加载指定文件。资源必须位于技能目录内，不能通过路径穿越读取外部文件。

## 创建和更新流程

1. 根据请求确定技能名称、适用范围和最小文件结构。
2. 检查目标目录是否已有技能；更新时保留仍然有效的内容和资源。
3. 编写简洁的 frontmatter 和只包含必要约束的入口说明。
4. 只有在重复执行或格式稳定性确实受益时才添加脚本；脚本必须说明输入、输出和失败行为。
5. 将模式专属内容放入 references，并在入口中按需路由，避免默认加载全部资料。
6. 用 Denia 的 `skill=list` 重新发现技能，再用 `skill=load` 检查正文和策略。
7. 检查名称、描述、路径边界、引用链接和脚本可执行性；发现失败时修复原因，不要静默忽略。

创建技能不会改变沙箱、权限模式或审批策略。涉及写入项目、用户目录或执行外部副作用时，仍遵循当前会话的授权边界。
